# 第三方微信协议接入操作指南

适用项目：本仓库 `wechat-bot`；现有接入为 `wechaty-puppet-wechat4u@1.14.14` + `wechat4u@0.7.14`，AI 启动参数为 `--serve deepseek-free`。

目标：普通微信群内通过 @ 机器人对话，并验证手机切换账号或退出账号后，服务器会话能否继续收发消息。

本文是选型、实施与验收指南，不表示第三方协议已经接入。未指定服务商，因此不提供未经验证的服务商、下载地址、价格、API 路径或接口参数。标为“拟新增”的配置在当前项目中无效，必须先完成对应改造。

## 1. 明确验收条件

“iPad 协议”“Mac 协议”和“云端托管”是接入形式，不代表手机退出后一定在线，更不代表永久免扫码。会话最终仍受微信服务端控制；第三方协议还可能带来账号限制及聊天数据托管风险。

先把下面几种操作分开验收，不要用“手机离线”概括所有情况：

| 手机或服务器操作                       | 必须观察的结果                               |
| -------------------------------------- | -------------------------------------------- |
| 手机锁屏、微信进入后台                 | 群内消息仍能接收并回复                       |
| 手机断网或关机                         | 服务器独立收发，不依赖手机转发               |
| 手机从账号 A 切换到账号 B              | A 对应的机器人继续收发                       |
| 手机明确退出账号 A                     | A 对应的机器人继续收发，这是单独的硬性验收项 |
| 手机移除登录设备、修改密码或会话被撤销 | 服务报告失效并告警；不能要求绕过撤销继续工作 |
| Node.js 或服务器重启                   | 恢复现有有效会话，不重复创建新设备           |

如果服务商不能演示“切换账号”和“退出账号”两个独立场景，就不能认定它满足你的需求。所有恢复方案都只能恢复尚未被撤销的有效会话。

## 2. 申请试用与收集资料

先试用、再小范围接入。要求服务商针对实际微信版本、账号和服务器环境给出书面答复及演示，不以广告中的“稳定在线”为依据。

可直接发送以下需求给服务商：

> 我需要个人微信普通群机器人，服务器部署，接收群消息并识别真实 @，调用 AI 后回群。要求分别测试手机切换账号、明确退出账号后机器人持续收发；重启服务应恢复有效会话。请提供试用、当前维护版本、支持的地区和系统、协议/API 文档、会话失效规则、掉线事件、退款与数据删除方式，以及 Wechaty 兼容情况。

购买前收齐资料：

| 项目       | 必须确认                                                       |
| ---------- | -------------------------------------------------------------- |
| 产品与维护 | 当前版本、最近维护时间、当前可用演示、服务状态与支持渠道       |
| 部署形式   | 服务商托管，还是自己部署协议进程；需要的 CPU 架构和系统版本    |
| 接口       | SDK、HTTP、WebSocket、Webhook 或 Wechaty Puppet；具体版本      |
| 登录       | 申请二维码、查询扫码状态、确认登录、查询当前账号身份           |
| 会话       | session/device 标识存在哪里、有效期、续期、重启恢复、并发限制  |
| 消息       | 稳定 message ID、群 ID、发送人 ID、真实 @ 列表、发送文本接口   |
| 事件投递   | 签名算法、重试条件、超时、重复事件、断线补拉或游标             |
| 发送语义   | 长度限制、速率限制、幂等键、超时后的结果查询方式               |
| 网络       | API 域名和端口、是否需要公网回调、IP 白名单、是否绑定服务器 IP |
| 数据       | 是否保存完整聊天记录、日志保留期、token 与票据托管方式         |
| 费用       | 试用时长、设备数、调用配额、流量、掉线期间计费、退出与退款     |

不要向服务商提交微信密码、短信验证码或不必要的完整账号资料。按核实过的登录流程使用专用测试账号扫码。

## 3. 选择接入路径

| 路径                         | 适用条件                                | 项目改造量                                      |
| ---------------------------- | --------------------------------------- | ----------------------------------------------- |
| Wechaty 兼容 Puppet/远程服务 | 服务商明确支持当前或指定的 Wechaty 版本 | 较小，主要替换 bot 构造与配置，仍须验证消息语义 |
| 独立 HTTP/WebSocket API      | 只有服务商自己的登录、收发消息接口      | 较大，增加事件接收、消息映射、去重及发送适配    |

优先评估第一条，但不要为了少改代码接受未维护的 Puppet。所谓“兼容微信”不等于兼容 Wechaty。

推荐的部署关系：

```text
普通微信群
    ↕
第三方协议服务（托管或独立部署，持有微信会话）
    ↕ 认证 API / 事件流
wechat-bot（白名单、@ 判断、AI 调用、消息发送）
    ↕
deepseek-free 对应的 AI 服务
```

扫码、会话续期和设备状态属于协议服务；AI 服务不能修复微信会话失效。

## 4. 准备服务器与备份

在当前服务器项目目录执行只读检查：

```bash
cd /home/ubuntu/wechat-bot
git status --short
git rev-parse HEAD
node --version
npm --version
uname -m
df -h .
```

记录当前 commit 作为回退版本。确认第三方 SDK 支持当前 Node.js、Linux 和 CPU 架构后再安装；不要直接把本机 `node_modules` 拷贝到服务器。

使用服务器快照或受限备份目录保存 `.env`、`WechatEveryDay.memory-card.json`（若存在）和需要保留的 `.data/wechat`。会话文件按凭据保护，备份不提交 Git，也不通过聊天发送。旧 Web 会话不能假定可导入新协议。

公网回调使用你控制的域名和有效 HTTPS 证书。只开放实际需要的入口；协议管理端口、Redis 和数据库不要直接暴露公网。只使用出站 WebSocket 的方案通常不需要额外开放回调端口，以服务商文档为准。

自部署协议服务只从核实过的发布渠道获取固定版本镜像或安装包，使用持久卷保存服务商规定的会话目录，限制管理接口访问。卷路径与健康检查命令必须按该产品文档填写。

## 5. 先独立验证协议服务

先用服务商控制台、官方示例或调试工具验证协议，不接 AI，避免把登录问题和模型问题混在一起。

1. 创建试用应用或设备槽位，领取 API 凭据，并按要求设置服务器 IP 白名单。
2. 配置消息事件接收方式；先准备验签与事件查看工具，再订阅事件，避免首批消息丢失。
3. 调用文档中的“创建或恢复会话”操作。首次才创建；后续尽量复用同一 session/device 标识。
4. 获取登录二维码，用测试微信号扫描并确认。二维码和登录 URL 不应公开分享。
5. 查询账号身份，确认返回的是预期账号 ID，再等待协议明确报告可收发状态。
6. 将账号加入专用测试群，发送唯一文本，例如 `protocol-check-001`；确认事件里能拿到 message ID、群 ID 和发送人 ID。
7. 用发送文本接口向同一测试群回复，记录发送结果或回执。
8. 用微信成员选择器真正 @ 测试账号，确认事件包含该账号的 mention ID；普通文本写一个同名字符串不能替代这个测试。
9. 分别完成手机切换账号、退出账号测试，再做协议进程重启与会话恢复测试。

若第 9 步不满足需求，先联系服务商，不进入项目迁移。进程显示在线、心跳成功或登录状态为 true，都不能代替真实群消息双向收发。

建议保存以下脱敏记录：测试时间、服务版本、手机微信版本、操作步骤、事件 ID、收发结果、离线原因及是否重新扫码。

## 6. 路径一：Wechaty 兼容服务

### 6.1 确认并安装指定适配器

让服务商明确给出 Puppet 包名、版本、导入方式、token 格式、endpoint 配置、TLS 要求及匹配的 Wechaty 版本。按文档安装固定版本，并提交 `package.json` 的变更。

不要把第三方 token 填进当前 `.env` 后就认为接入完成。当前 `src/platforms/wechat/bot.js` 将 Puppet 写死为 `wechaty-puppet-wechat4u`；`uos: true` 也不是通用的第三方协议开关。

### 6.2 改造配置与构造逻辑

建议新增一个协议选择配置，由 `src/config/env.js` 读取，再由 `src/platforms/wechat/bot.js` 选择不同的构造方式。具体变量可按项目实现确定：

```dotenv
# 拟新增配置，当前代码尚未读取，不能直接生效。
WECHAT_TRANSPORT='vendor'
WECHAT_VENDOR_TOKEN=''
WECHAT_VENDOR_ENDPOINT=''
```

实施要求：

1. 保留原 Web 协议分支用于回退，新协议分支按官方示例实例化 Puppet。
2. 只有新协议分支检查第三方凭据，不把旧协议的 `uos` 或 `CHROME_BIN` 盲目传给新服务。
3. 登录状态文件按协议、账号分开保存，不复用同一个旧 Web memory-card。
4. 当前 `DiagnosticWechat4u` 使用旧适配器内部钩子，仅保留在 `wechat4u` 分支，新协议使用其自身的脱敏诊断。
5. 尽量复用现有 scan/login/logout/message/error 处理，但先确认该 Puppet 的扫码及就绪事件语义。

### 6.3 验证现有消息代码是否兼容

`src/wechaty/sendMessage.js` 和消息捕获代码依赖：`message.text()`、`type()`、`talker()`、`to()`、`room()`、`mentionText()`，以及联系人名称、备注、群名和 `say()` 等能力。

当前 @ 判断依靠 `content.includes(BOT_NAME)`，机器人自身判断也依赖名称；更换协议时应改为根据账号 ID 和真实 mention 列表判断，并测试群昵称变化、同名成员、@ 其他人和机器人自身消息。不能假定所有 Puppet 都以相同文本格式表示 @。

先用固定回复验证收发，再启用 `getServe('deepseek-free')`，最后开启需要的本地消息记录与命令。

## 7. 路径二：独立协议 API

### 7.1 接口映射表

以下是“能力名称”，不是可直接请求的 API 路径；实际 HTTP 方法、路径、签名和字段必须来自服务商文档。

| 项目需要的能力 | 服务商接口或事件需提供                                          |
| -------------- | --------------------------------------------------------------- |
| 首次登录       | 申请二维码、扫码状态、登录完成事件                              |
| 恢复会话       | 查询并恢复已有 session/device，区分有效与已撤销                 |
| 当前账号       | 稳定的 self user ID                                             |
| 接收消息       | 群 ID、发送人 ID、message ID、正文、类型、时间、mention ID 列表 |
| 回复群聊       | 按群 ID 发送文本，返回结果或消息 ID                             |
| 断线恢复       | 状态事件、重连方式、消息游标或补拉规则                          |

### 7.2 推荐代码边界

新增供应商适配器，集中处理认证、HTTP/WS 调用和错误转换；新增微信 API 通道入口，处理事件投递、白名单和业务调度。继续复用 `src/wechaty/serve.js` 的 AI 服务选择，不要复制整个模型调用模块。

现有 `defaultMessage` 接收的是 Wechaty 对象，不能直接传入供应商 JSON；现有 `captureWechatMessage` 也有相同限制。可实现完整兼容对象，或为新通道使用标准化消息结构并单独接入存储。推荐后者，减少对 Wechaty 内部约定的依赖。

建议内部字段如下，它们不是供应商真实字段：

```json
{
  "provider": "selected-vendor",
  "accountId": "bot-account-id",
  "messageId": "vendor-message-id",
  "roomId": "vendor-room-id",
  "senderId": "member-id",
  "text": "问题正文",
  "mentionedUserIds": ["bot-account-id"],
  "isSelf": false
}
```

### 7.3 事件处理顺序

1. 校验事件来源、签名与服务商规定的时间窗口；未验证的请求不进入消息业务。
2. 按 `provider + accountId + messageId` 去重，并将事件持久化或加入持久队列。
3. 按服务商要求及时确认接收。不要等 AI 回复后才返回 HTTP 成功；AI 延迟可能触发供应商重试。
4. 排除自身消息、历史补发中不应回复的事件及非文本类型。
5. 按稳定群 ID 检查白名单，按账号 ID 检查真实 @；提取正文并忽略空问题。
6. 调用 `getServe('deepseek-free')` 获取回复；限制并发、超时和队列长度。
7. 按协议长度限制拆分消息，并通过适配器发送回原群，记录处理与发送状态。
8. 对重复事件返回既有处理结果，避免重复调用 AI 和重复发送。

如果发送超时但服务端已接受，直接重发可能重复回复。优先使用供应商幂等键或结果查询；不支持时应记录“发送结果未知”，不要宣称实现严格恰好一次。

### 7.4 Webhook 与 WebSocket

Webhook：按服务商签名规则保留原始请求字节，验证后解析；明确接收 URL、HTTPS、响应格式、重试间隔与最大请求大小。不要凭空设计一套供应商不支持的签名算法。

WebSocket：使用认证连接，按文档发送心跳；网络断线按指数退避并加入随机延迟重连，持久化可恢复游标。没有补拉功能时，应明确断线期间可能丢消息。

无论哪种方式，日志只记事件标识、状态和脱敏错误，不输出 token、Cookie、二维码链接或完整登录响应。

## 8. 配置群聊与 AI

以下是当前项目已有配置示例，昵称和群名需换为真实值：

```dotenv
BOT_NAME='@测试助手'
ROOM_WHITELIST='机器人测试群'
ALIAS_WHITELIST=''
AUTO_REPLY_PREFIX=''
SERVICE_TYPE='deepseek-free'
WECHAT_STORE_MESSAGES='false'
ENABLE_REMOTE_OPENCLI='false'
```

`WECHAT_STORE_MESSAGES=false` 仅关闭项目本地消息记录，不控制服务商的日志保留。测试期间可按需要调整。

保留服务器上已有的 `DEEPSEEK_FREE_URL`、`DEEPSEEK_FREE_TOKEN`、`DEEPSEEK_FREE_MODEL` 等模型配置。第三方微信凭据与 AI token 是两套独立凭据。

采用独立 API 路径时，需要实现按群 ID 的新白名单配置；上面的群名白名单不会自动被新入口使用。群内有同名群、改群名或群昵称变化时，稳定 ID 比名称更可靠。

## 9. 运行与会话恢复

改造和验收通过后，先前台启动观察一次完整登录及群回复。若继续沿用原 CLI 入口：

```bash
cd /home/ubuntu/wechat-bot
npm run start -- --serve deepseek-free
```

该命令在未修改接入层之前仍使用旧协议。独立 API 通道如果新增了 CLI 子命令，应使用该实现对应的命令。

前台验证后停止前台进程，确保同一微信会话只有一个主动消费者，再交给已安装的 PM2：

```bash
pm2 list
pm2 start npm --name wechat-bot --cwd /home/ubuntu/wechat-bot -- run start -- --serve deepseek-free
pm2 save
pm2 startup
```

只有不存在同名任务时才执行 `pm2 start`；已有任务且启动参数、目录一致时使用 `pm2 restart wechat-bot --update-env`。按 `pm2 startup` 输出执行它要求的系统命令，再核对开机恢复。配置日志轮转，避免磁盘被日志写满。

协议服务和业务进程分开管理。仅重启业务进程时，不应重新申请二维码或创建新的设备槽位。启动恢复流程应为：读取会话标识 → 查询协议状态 → 恢复订阅 → 恢复队列；仅当明确要求重新认证时才进入扫码流程。

建议实现状态：`WAITING_SCAN`、`ONLINE`、`RECONNECTING`、`AUTH_REQUIRED`、`STOPPED`。网络错误可退避重试，授权失效应告警并等待扫码，不能无限重试登录。

健康检查分别记录：业务进程存活、协议账号状态、最近收到事件时间、发送失败数、队列积压及 AI 调用失败数。群暂时没有消息不等于离线；仅进程存活也不等于微信在线。

## 10. 验收测试

先使用固定文本回复测试协议，再使用 AI 测试完整链路。每条用例从其他群成员账号发消息，记录唯一编号、收到事件时间、回复时间、协议状态和是否要求扫码。

| 用例 | 操作                                   | 通过标准                             |
| ---- | -------------------------------------- | ------------------------------------ |
| T01  | 白名单群真正 @ 机器人提问              | 回复原群，且只回复一次               |
| T02  | 不 @、@ 别人、仅输入同名文字           | 不误回复                             |
| T03  | 非白名单群 @                           | 不回复                               |
| T04  | 机器人自己发消息                       | 不形成自回复循环                     |
| T05  | 手机锁屏、后台、断网分别测试           | 每个场景持续双向收发                 |
| T06  | 手机 A 切换到 B                        | A 的机器人持续收发，不重新扫码       |
| T07  | 手机明确退出 A                         | A 的机器人持续收发，不重新扫码       |
| T08  | 重启 Node.js、协议服务、服务器分别测试 | 有效会话恢复，不重复回复旧消息       |
| T09  | 短暂网络中断后恢复                     | 可重连；补拉或丢消息边界有记录       |
| T10  | 重复投递同一 message ID                | 不重复调用 AI 或发送回复             |
| T11  | AI 超时、发送限流                      | 有明确状态，不无限重试或阻塞其他群   |
| T12  | 会话被撤销                             | 明确转入需认证状态，告警，不伪装在线 |

建议 T06、T07 分别做短时检查和至少 24 小时观察，再进行 72 小时持续运行验证。这是验收窗口建议，不是永久在线的证明。测试账号、微信版本、协议版本或服务器地域改变后，关键用例应重新验证。

T07 失败就代表未满足“手机退出也不影响”的原始要求，即使其他用例全部通过。

## 11. 故障处理与回退

| 现象                 | 优先排查                                                    |
| -------------------- | ----------------------------------------------------------- |
| 手机退出后掉线       | 协议能力和服务端会话规则；不要先改 AI 配置                  |
| 显示在线但收不到事件 | 订阅、回调验签、网络、消费游标、实际登录账号                |
| 能收消息但 @ 不回复  | mention ID 映射、群 ID 白名单、自身消息过滤                 |
| 能触发但不回复       | AI 配置、超时、发送接口、限流和消息长度                     |
| 重启总要求扫码       | session/device 标识是否复用、持久卷是否丢失、会话是否已撤销 |
| 同一消息多次回复     | 供应商重试、多个消费者、去重存储、发送结果未知后的重发      |

回退步骤：

1. 停止新通道消费和发送，记录队列中未处理与发送结果未知的消息。
2. 按服务商文档停用订阅或断开会话，避免新旧通道同时自动回复。
3. 恢复已记录的旧版本到独立发布目录，并使用其对应的配置和依赖；保留当前变更，不使用强制重置覆盖未知改动。
4. 切回旧 Web 协议入口，必要时重新扫码，再验证测试群。
5. 停止服务商试用或计费前，导出所需脱敏记录并按其流程删除托管会话。

回退只能恢复旧方案，不能消除原来的 `webwxinit Ret=1` 问题，也不能让旧协议满足手机退出后保持在线的要求。
